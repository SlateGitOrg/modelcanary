# Design decisions

Key design decisions in modelcanary, each with the reasoning and what it would cost if it turned out wrong, in the form `- <decision> — <why> — <cost if wrong>`.

## Statistics

- compare the two arms on **paired** observations (shadow: same request; canary: FIFO-matched requests from independent arms) and run one-sample sequential tests on the per-pair degradation — every procedure then has a single i.i.d. stream with mean equal to the true difference, which is what SPRT and confidence sequences assume — cost if wrong: canary surplus on the baseline arm is discarded (bounded buffer), so ~2x more baseline traffic is generated than used.
- error rate uses a **discordant-pair SPRT** (sequential McNemar) on `P(candidate is the wrong one | exactly one wrong) = OR/(1+OR)`, H0 `OR = 1` vs H1 `OR = odds_ratio` — under H0 this probability is exactly 0.5 for independent *and* for exchangeable correlated (shadow) pairs, so the type-I guarantee does not depend on the correlation between models — cost if wrong: a pure odds-ratio H1 says nothing about absolute differences; `derive_truth` therefore calls a candidate WORSE on error only if both the odds ratio and the absolute margin are exceeded.
- an always-valid **discordance-rate bound** (betting CS, half the promotion budget) can also clear the error metric, because `p_c - p_b <= P(discordant)` — the SPRT never decides when two models agree on every request (a re-export or a refactor would otherwise always time out and roll back) — cost if wrong: the SPRT's beta is halved, so non-inferiority on error takes somewhat more discordant pairs.
- latency uses the **asymptotic normal-mixture CS** (Waudby-Smith et al. 2021) with a plug-in variance; conversion uses the **hedged-capital betting CS** (Waudby-Smith & Ramdas 2023) on differences in [-1, 1] — latency is unbounded and heavy-tailed (no finite-sample bounded-data method applies), conversion is bounded so a non-asymptotic method is available and preferred — cost if wrong: the latency CS is only asymptotically valid; the coverage test on lognormal data checks it empirically, not as a theorem.
- CS intersections **restart** when a new interval is disjoint from the running intersection, counting `resets` — freezing a stale interval would make a regression that appears mid-rollout invisible (found by a failing test) — cost if wrong: under stationarity the restart is a probability-≤α event, so validity is unaffected; under drift the CS is no longer a CS for a single mean and only acts as a change detector.
- split each budget across metrics with **Bonferroni** (`budget / n_metrics`) — simple, valid under any dependence between metrics — cost if wrong: conservative; with 3 metrics each test runs at 1/3 of the budget, so decisions take longer than a dependence-aware split would.
- a single two-sided CS at `min(alpha_rollback, alpha_promotion)` serves both the rollback and the promotion decision for a metric — the same interval answers "lower > rollback_margin" and "upper < tolerance" without double-spending — cost if wrong: each one-sided error is at most α (often ≈ α/2), so the CS monitors are conservative.
- `rollback_margin` (default 0) decides what "confidently worse" means per metric; the demo sets 0.5 ms for latency with a 1 ms tolerance — with margin 0 any statistically certain slowdown (e.g. +0.13 ms for a more accurate SVC) rolls back; the margins are wide because wall-clock inference time on a shared machine roughly doubles under load (observed while the evaluation ran in parallel), which is not what an operator who wrote "0.5 ms tolerance" wants — cost if wrong: a regression between 0 and the margin is tolerated by design.

## Evaluation

- the fixed-horizon comparator is a **one-sided non-inferiority z-test** at the power-analysis sample size `((z_{1-α} + z_{1-β}) σ / margin)^2`, with `σ` taken from an A/A **pilot on reserved tuning seeds 0..19** — that is how a fixed-horizon test is planned in practice, and keeping pilot seeds disjoint from evaluation seeds (≥ 1,000,000, enforced by `eval_seeds`) avoids tuning on the reported data — cost if wrong: the pilot uses canary-style independent pairs, so the horizon is conservative for shadow pairs.
- "peeking" (repeating the fixed-sample z-test at every check) is included as a third strategy — it quantifies the failure mode sequential tests exist to fix — cost if wrong: none for the product; it is only an evaluation baseline.
- false rollback is counted on BETTER/EQUAL truths only and **includes** budget-exhausted inconclusive rollbacks; INDIFFERENT scenarios (degradation strictly inside the tolerance) are excluded from both rates — there is no wrong answer inside the indifference zone — cost if wrong: the standard suite has no INDIFFERENT scenario, so behaviour there is unmeasured.
- simulated labels arrive immediately and latency/error draws are i.i.d. within a run — keeps the evaluation about the statistical procedures — cost if wrong: real feedback delay and diurnal drift are not evaluated (listed under Limitations).

## Serving

- shadow scoring runs in a FastAPI `BackgroundTasks` job after the response — the user-visible latency is the production model's only — cost if wrong: under load, feedback can arrive before the shadow score; such feedback is counted as matched-but-unpaired and discarded rather than guessed.
- canary assignment is a salted blake2b hash of the request's routing key (salt = rollout id) — sticky per user, monotone as the weight grows, independent across rollouts — cost if wrong: clients that omit routing keys get a random key per request (no stickiness).
- latency is one observation per model call (time inside `InferenceSession.run` only), not per row — avoids pseudo-replication when a batch is split between arms — cost if wrong: batched requests mix batch sizes into the latency metric; the demo sends single-row requests.
- candidate inference failures fall back to production for that request and feed a **failure-rate guardrail** checked before any statistics — a crashing model must not need a statistical test to be stopped — cost if wrong: the guardrail is a plain threshold (`> 2%` after 50 attempts), not a sequential test.
- promotion requires `min_candidate_requests_before_promote` live requests (500 by default) besides all-NOT_WORSE — a model cleared entirely in shadow would otherwise be promoted at the first canary check with zero real exposure — cost if wrong: slows promotion of clearly good candidates slightly.
- Prometheus text exposition is generated by a 50-line counter class instead of `prometheus_client` — five counters do not justify a dependency — cost if wrong: no histograms; latency distributions are in the rollout snapshot instead.
- the audit log is a SHA-256 **hash chain** in JSONL — tamper-evident with no infrastructure — cost if wrong: an attacker who can rewrite the whole file can recompute the chain; anchoring the head hash externally is on the roadmap.

## Tooling

- `httpx2` replaces `httpx` for Starlette's `TestClient` — the installed Starlette deprecates `httpx` with a warning that the strict `filterwarnings = error` setting turns into a failure — cost if wrong: one more pinned dependency in the dev/demo groups.
- scikit-learn / skl2onnx / httpx2 are an optional `demo` extra (also used by tests), not runtime dependencies — the gateway itself only needs onnxruntime, numpy, scipy, pydantic, FastAPI and uvicorn — cost if wrong: `make` targets install all extras, so this is invisible unless the package is installed without them.
- the demo's business outcome (conversion) is **simulated** from correctness (P = 0.30 if correct, 0.10 if wrong) — the digits dataset has no business signal — cost if wrong: the conversion numbers in the demo are illustrative, not evidence.
